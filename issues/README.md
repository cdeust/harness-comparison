# Capstone issue registry

This registry contains the engineering and research work that remains after a
current-source audit. It is not an import of another backlog. A record appears
here only when it can be tied to the research contract and evaluated against a
pinned repository revision.

## Addressing

Every record has one unambiguous address:

`issues/<project>/<category>/<subject>.md`

- `project` identifies the repository or benchmark infrastructure that must
  change;
- `category` identifies the measured capability or quality boundary;
- `subject` identifies one falsifiable defect or one missing measurement.

Project-level and category-level indexes are navigation aids. They are never
substitutes for an issue dossier.

## Evidence verdicts

The public proof vocabulary is deliberately small:

| Verdict | Meaning | May claim a current product defect? |
|---|---|---|
| `proven` | Reproduced at a pinned revision with an immutable artifact and an external oracle. | Yes, within the recorded scope. |
| `pending` | Current source supports a falsifiable hypothesis, but the required runtime or matched benchmark has not passed. | No. |
| `blocked` | The prescribed evaluation cannot run because a declared prerequisite is unavailable. | No. |
| `unsourced` | No current, checkable evidence supports the statement. | No; it stays outside the active registry. |

An issue being open elsewhere is not evidence that a defect still exists.
Historical benchmark output is not normative. The rules in this repository's
versioned Markdown research contract prevail.

## Categories

| Category | Capstone boundary |
|---|---|
| `benchmark-validity` | Preregistration, matched execution, independent scoring, contamination, publication. |
| `code-intelligence` | Indexing, retrieval, navigation, impact analysis, freshness. |
| `critical-reasoning` | Contradiction handling, refusal, decision quality, human escalation. |
| `data-sovereignty` | Ownership, export, deletion, migration, local/offline operation. |
| `documentation` | Reproducible installation, contracts, limitations and provenance. |
| `finops` | Measured model/tool cost, budget enforcement and provider replaceability. |
| `integration` | Claude/Codex parity, MCP contracts and complete-stack composition. |
| `memory` | Persistence, retrieval quality, freshness and cross-project isolation. |
| `network-security` | Listeners, egress, credentials, TLS, injection and unauthorized writes. |
| `observability` | Traces, logs, metrics, failure visibility and evidence export. |
| `orchestration` | State machines, delegation, recovery and deterministic control loops. |
| `provenance` | Source attribution, decision lineage, reversibility and conflict history. |
| `reliability` | Silent failure, concurrency safety, recovery and regression protection. |
| `scalability` | Workload ladders, saturation, latency, throughput and resource economics. |

## Publication gate

Each dossier must satisfy [SCHEMA.md](SCHEMA.md). In particular, it must cite
the applicable research rule, pin the inspected source revision, state what is
not yet known, and define acceptance through observable signals. A fix closes
the issue only after the smallest affected benchmark slice passes; a changed
stack or protocol also requires the full regression matrix.

The current source audit and disposition totals are published in
[AUDIT.md](AUDIT.md), with one-to-one coverage in
[AUDIT-LEDGER.md](AUDIT-LEDGER.md).
